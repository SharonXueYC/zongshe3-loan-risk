## 第 3 页｜课题背景与需求洞察

### 页上正文

**多源数据融合的必要性**  
仅依赖系统内存储的信用分，难以全面反映借款人的实际风险水平。依据任务书要求，本系统在风控评估中引入外部征信信息与运营商特征，与库内数据共同参与决策。

**可解释的评分卡机制**  
课程要求采用评分卡机制，且风控结论须具备可追溯性。本系统未采用黑盒模型，而采用「评分卡计分 + 规则链硬性拦截」：各维度分值及触发拒绝的具体规则，均可在管理端界面与数据库中查询。

**原型验证与工程扩展**  
受课程环境限制，系统无法直连生产级征信 API。本组采用 Jsoup 解析演示 HTML 表格模拟外部数据源，经 **Adapter 适配器** 接入风控流程；后续对接真实接口时，仅需新增 Adapter 实现类，无需修改评分卡核心逻辑。

**多端协同**  
系统按用户 H5、管理 Web、Spring Boot 后端三条业务线组织实现。对外统一暴露单一 IP，由 Nginx 分别转发 `/`、`/admin/`、`/api/` 路径，移动端以相对路径访问 API，无需额外配置跨域策略。

### 汇报讲解（约 1 分 10 秒）

本课题的核心在于完成多源数据接入风控流程，并使评估结果具备可解释性，而非仅实现借款页面展示。

综设 I 阶段已完成用例分析与数据库设计；综设 II 阶段的重点是贯通申请、审批、合同、放款、还款等业务链路，并落实任务书所要求的评分卡机制与数据爬取模块。

针对外部征信接口无法在课程环境中直连的问题，本组通过爬虫解析演示页面并将结果写入缓存表，风控模块经适配器读取上述数据，使演示环境与未来对接真实 API 时采用一致的处理流程。

## 第 4 页｜总体架构设计与技术选型

### 页上总述

**系统在开发层面采用前后端分离，在部署层面经 Nginx 聚合为统一访问入口。**

- 用户 H5（`apps/uni-client/`）、管理端 Vue（`frontend/`）、后端 Spring Boot（`backend/`）为三个独立工程，接口规范统一于 Swagger；前端通过 fetch 调用 JSON 接口，后端不承担页面渲染。
- 部署后 Nginx 监听 80 端口：`/` 提供用户页面，`/admin/` 提供管理端，`/api/` 反向代理至后端 8080 端口。浏览器侧视为同一站点，因而不产生跨域访问问题。
- 后端采用**单体 Spring Boot** 架构（单 JAR 部署），按 `modules/` 划分业务包，便于在本课程规模下交付与联调。
- 爬虫模块独立调度，结果写入 `t_external_data_cache`；风控侧 `MockCreditBureauAdapter` 等组件读取缓存或执行兜底算法，数据获取与风控计算在模块层面相互独立。

### 左栏｜分层与数据流

在接入层，Nginx 作为 Docker Compose 中的 `web` 服务运行，统一承担静态资源托管与 API 反向代理。数据获取方面，爬虫模块使用 Jsoup 解析 `demo-credit.html` 与 `demo-telecom.html`，解析结果按 `SUFFIX_0`～`SUFFIX_9` 写入外部数据缓存。持久化层采用 MySQL，存储用户、贷款、合同、还款计划及 `t_risk_report` 等业务数据；Redis 主要用于短信验证码等短生命周期数据的存取，与业务主库职责分离。

### 右栏｜技术栈

后端基于 Java 21 与 Spring Boot 3.2.5，集成 JPA、Security 及定时任务；安全认证采用 JWT 与 BCrypt，用户端与管理端分别登录，请求头携带 Bearer Token。管理端使用 Vue 3、ECharts 与 fetch 实现，未引入 Element Plus 与 Axios；用户端采用 HTML 多页应用（MPA），主要页面包括 `main-home.html`、`loan-home.html` 等。部署采用 Docker Compose，编排 mysql、redis、backend、web 四个容器；测试使用 JUnit5 与 Mockito，共编写 13 条 Service 层单元测试。

### 汇报讲解（约 1 分 20 秒）

关于「前后端分离」与「Nginx 统一入口」的关系，二者分属不同层面，并不矛盾。前后端分离指代码与职责的划分：前端负责展示与交互，后端负责业务逻辑与数据持久化，二者通过 REST 接口通信。Nginx 统一入口属于部署与访问层面的设计：对外提供单一 IP 与端口，移动端无需硬编码后端地址，亦无需在 Spring Boot 中单独配置 CORS。

在技术选型方面，后端采用 Spring Boot，便于实现分层架构与安全认证；管理端采用 Vue 3，便于表格展示与 ECharts 图表集成；用户端采用原生 H5 多页结构，便于 Nginx 直接托管静态资源并独立维护各页面。存储方面，MySQL 承担业务数据持久化，Redis 承担验证码等临时状态存储，职责划分明确。

## 第 5 页｜多数据源融合工程实现

### 页上总述
                                                                                     
外部数据进入风控模块的路径为：**爬虫解析 → 写入缓存表 → 适配器读取 → 生成 FeatureSnapshot（特征快照）**。评分卡引擎与规则链仅依赖快照中的统一字段，与数据来源于爬取或 API 无关。

### 三个要点

**① 爬虫调度与数据落库**  
`DataCrawlerService` 使用 Jsoup，按选择器 `table#credit-data tbody tr` 解析表格；支持定时任务（约每 6 小时执行一次）及管理员手动调用 `POST /api/admin/crawler/run`。数据按身份证或手机**末位 0～9** 写入缓存，例如末位 9 对应逾期 3 次。

**② 适配器与兜底机制**  
`MockCreditBureauAdapter`、`MockTelecomAdapter` 优先读取 `t_external_data_cache`；若缓存尚未生成，则按末位算法提供默认值，保证演示流程可连续执行。

**③ 扩展方式**  
对接真实征信 API 时，仅需新增 `CreditBureauAdapter` 实现类，`SimpleScoringCardEngine` 与 `RiskRuleEvaluator` 规则链无需修改，该设计为系统预留了明确的替换路径。

### 汇报讲解（约 1 分 30 秒）

多数据源融合为本课题名称中的核心要求，建议结合测试用例 RC-06 进行说明。

演示数据位于 `backend/src/main/resources/crawler/` 目录下的两个 HTML 文件中，表格结构与征信报告形式相近。爬虫执行完成后，缓存表中将写入 10 条记录，分别对应身份证末位 0 至 9。

用户提交贷款申请时，后端根据身份证号匹配相应缓存记录，将逾期次数、在网月数等字段写入 `FeatureSnapshot`。同一快照同时供评分卡计分与「逾期次数大于 2 次即拒绝」等硬性规则使用。

答辩演示时，可通过 Swagger 调用爬取接口，再对指定申请调用 `POST /api/risk/applications/{id}/assess` 重新评估；管理端刷新后即可观察到评分变化。该流程模拟了生产环境中外部数据更新后重新执行风控评估的场景。

## 第 6 页｜评分卡引擎与业务状态机

### 页上总述

风控评估分为两层：**评分卡**负责计算 0～100 分并与 40 分阈值比较；**规则链**对信用分过低、逾期过多等情形实施硬性拒绝。两层评估结果一并写入 `t_risk_report`，管理端与用户端仅负责展示，不参与计算。

### 评分卡规则

| 维度 | 分箱 | 分值 |
|------|------|------|
| 基础信用分 | ≥700 / ≥600 / ≥500 / 其他 | 50 / 35 / 20 / 5 |
| 申请金额 | ≤5万 / ≤20万 / >20万 | 30 / 20 / 10 |
| 征信逾期 | 0 / ≤2 / >2 次 | +10 / 0 / **−20** |
| 运营商在网 | ≥24月 / ≥12月 / 其他 | +10 / +5 / 0 |

**满分 100 分，通过阈值 40 分**（配置项 `risk.scoring-card.pass-min-points=40`）。  
逾期 **>2 次** 除在评分卡中扣分外，还将触发 `ExternalDataRiskEvaluator` 的**硬性拒绝**。

### 业务状态机

```
pending ──审批通过──► approved ──签署──► 合同流程 ──放款──► disbursed ──还清──► SETTLED
   └──审批拒绝──► rejected
```

**联调阶段的两项重要调整：**

1. **提交即风控**：用户提交申请后立即生成风控报告，管理端不再出现长期「未评估」状态；系统启动时通过 `backfillRiskReports()` 为历史演示数据补全报告。  
2. **审批通过后再生成还款计划**：早期实现在提交阶段即生成计划，导致用户端还款页出现未审批贷款；现已调整至 `approve` 环节生成，并在查询层过滤贷款状态。

### 汇报讲解（约 1 分 20 秒）

评分卡机制的优势在于评估过程可逐项说明。例如：信用分 720 对应 50 分，申请金额 3 万元对应 30 分，无逾期记录加 10 分，在网时长超过 24 个月再加 10 分，合计 100 分。

若身份证末位为 9，爬取后逾期次数变为 3 次，该维度扣 20 分，总分可能由 80 分降至 60 分；若同时满足「逾期大于 2 次」的硬性规则，即使总分未低于阈值，申请仍将被拒绝。

在业务状态机方面，审批、合同、放款、还款须按序执行。关键写操作采用 `@Transactional` 保证事务一致性；放款前查询是否已有成功放款记录，以防止重复放款。

## 第 7 页｜多端协同与业务视图实现

### 页上总述

借款用户与管理员所见的业务视图不同，但共用同一套后端 API 及 JWT 鉴权机制。

- **管理端**：基于 Vue 3 的单页应用，控制台图表数据来源于 `/api/statistics/dashboard` 与 `/charts` 接口，已与后端统计服务联调对接。  
- **用户端**：由多个 HTML 页面构成，首页采用功能入口网格布局；借款页在调整金额、期限时可实时重算月供（等额本息/等额本金在前端计算，无需每次请求后端）。  
- **还款操作**：经 `payment.html` 二次确认后再提交，降低误操作风险。

### 管理端实现要点

管理端贷款列表展示 `riskPassed`、评分卡分值及拒绝原因等字段；审批操作完成后刷新列表。合同模块支持签署与放款，并与控制台最近贷款、月度还款统计联动。

统计图表曾出现未来月份仍显示数据的问题，经后端按**实际还款日期**（`repayTime`）聚合，并由前端 `barChartMonthCount` 限制展示月数后，已与管理端数据保持一致。

### 用户端实现要点

用户端采用原生 H5 多页结构，便于页面独立维护及 Nginx 静态托管。`js/user-session.js` 统一处理 Token 注入；退出登录通过 `/?logout=1` 清除 localStorage，避免演示终端长期保持登录状态。

借款记录在 `loan-records.html` 中展示，`disbursed` 等状态已映射为中文「已放款」等文案。

### 汇报讲解（约 1 分钟）

两端职责划分如下：用户端承担借款申请、进度查询、还款等业务办理；管理端承担数据统计、贷款审批、风控明细查阅及放款操作。

联调阶段，前后端首先在 Swagger 文档中对齐字段定义（如 `statusText`、`scoringCardPoints`），再分别实现界面，以减少返工。

## 第 8 页｜三层测试体系与质量保障

### 页上总述

测试工作按三个层次递进展开：**单元测试**验证 Service 层业务逻辑，**风控专项测试**验证多源融合对评分结果的影响，**全链路功能测试**验证三端联调及数据库状态的一致性。

### 三层说明

- **L1 单元测试层**：采用 JUnit5 与 Mockito，共编写 13 条用例，`mvn test` 全部通过；覆盖合同模块 6 条、贷款模块 2 条、评分卡与风控模块 4 条、爬虫模块 1 条，重点验证 Service 层业务逻辑。
- **L2 风控专项测试层**：设计 RC01～RC10 共 10 条用例；其中 **RC-06** 针对身份证末位为 9 的用户，对比爬取前后调用 assess 接口时 `scoringCardPoints` 与 `passed` 字段的变化，用于验证多源数据融合对评分结果的影响。
- **L3 全链路功能测试层**：设计 TC01～TC18 共 18 条用例，覆盖登录、申贷、审批、放款、还款等主流程；结合 Apifox 调用接口，并使用 Navicat 核查 `t_risk_report` 与还款计划等数据库状态。

### 汇报讲解（约 1 分钟）

单元测试采用 Mockito 隔离 Repository 层，不依赖真实数据库，重点检验 Service 层逻辑。例如「未审批不得生成合同」「不得跨用户签署合同」等问题，均在单元测试阶段发现并修复。

RC-06 用于验证外部数据对风控结果的实际影响：同一笔申请在爬取前后执行 assess，评分与通过状态可能发生变化，表明外部特征已正确进入评分卡计算。

全链路测试需同时检验三端表现：用户端提交后，管理端应即时显示风控评估结果；放款完成后，用户端还款页应出现相应还款计划。相关用例见项目测试文档及测试报告。

**说明：** 重复放款防护通过 `disburseRecordRepository` 查询数据库实现，**并非**基于 Redis 分布式锁。

## 第 9 页｜云端部署方案与工程难点攻坚

### 页上总述

系统采用 Docker Compose 在阿里云上编排 MySQL、Redis、backend、Nginx（web）四个容器。部署过程中遇到的主要问题及对应处理措施如下。

### 四个要点

**① 四容器编排**  
`deploy/docker-compose.yml` 定义服务依赖关系；`.env` 文件配置 `DB_PASSWORD`、`JWT_SECRET`、`ADMIN_PASSWORD` 等变量。修改 `.env` 后须执行 `docker compose up -d --force-recreate backend`，仅 restart 可能无法加载新环境变量。

**② 构建加速**  
云主机内存有限，容器内执行 Maven 构建曾出现 Network unreachable 或内存不足。本组在 `backend/settings.xml` 中配置阿里云 Maven 镜像；亦可于本机执行 `mvn package` 后，通过 `Dockerfile.prebuilt` 仅拷贝 JAR 包部署。

**③ 「风险未评估」问题修复**  
早期仅在手动调用 assess 时生成报告，管理端长期显示未评估。现已改为提交申请时自动执行风控，并在启动时通过 `backfillRiskReports()` 补全历史数据。

**④ 统计图表时序问题**  
控制台月度还款统计曾出现未来月份仍有数据的情况。经调整 `StatisticsServiceImpl`，按 `repayTime` 聚合并过滤未来月份后，统计结果已与实际还款情况一致。

### 汇报讲解（约 1 分 10 秒）

系统访问地址为：用户端 `http://47.109.202.165/`，管理端 `/admin/`，API 前缀 `/api/`。

部署流程概括为：上传代码 → 复制并编辑 `.env` → 执行 `docker compose up -d --build` → 通过 `docker compose ps` 确认四个容器均为 Up 状态。

部署过程中曾遇到 Windows 环境下脚本 CRLF 换行导致 bash 无法执行、`.env` 中含 `#` 注释导致 Docker 解析异常、MySQL 密码与 `.env` 不一致导致 backend 反复重启等问题，相关说明已写入 `deploy/README.md`。

## 第 11 页｜现场实操演示核心链路

### 演示步骤

## 附录 A｜答辩常见问题与参考答案

**问：前后端分离与 Nginx 同源访问是否矛盾？**  
答：二者分属不同层面，并不矛盾。前后端分离指开发架构：三个独立工程通过接口通信；同源访问指部署架构：Nginx 反向代理使三端对外呈现为同一站点。本地开发时前端与后端仍可分别运行于不同端口。

**问：用户端为何未采用 Vue 框架？**  
答：用户端页面数量相对有限、跳转关系清晰，采用 H5 多页结构便于独立维护与静态部署；管理端表格与图表较多，采用 Vue 3 更为合适。答辩演示以云上 H5 用户端为准。

**问：爬虫模块是否构成核心创新？**  
答：本课题的重点在于在无法对接真实 API 的条件下，通过「爬虫 + 缓存 + 适配器」完成多源数据融合链路的工程实现。其价值在于流程可演示、模块可替换，而非爬虫技术本身的复杂度。

**问：本系统与生产环境的主要差距？**  
答：演示 HTML 替代真实征信接口；部分身份核验界面为 UI 演示；尚未配置 HTTPS 与运维监控。Adapter 层与评分卡规则设计可延续至生产环境使用。
